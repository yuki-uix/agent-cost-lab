# 方向

> 这份文档回答两件事：**这个仓库现在是什么**，以及**它要长成什么**。
> 写在这里而不是散在各章里，是因为 2026-09-03 之前它只存在于口头，
> 而一个只在脑子里的方向，六周后就会变成另一个方向。

---

## 1. 现在是什么：一个度量装置，不是一个工具

`src/agentcostlab/` 是一台仪器：代理坐在真实调用路径上，记录实际发出的请求，
用一条经核实费率的公式把用量换算成钱，两道闸（归一化、导出）由测试而非清单守住。

它是为**回答三个实验**建的，不是为别人安装建的。当前的使用方式是
「把 agent 指向 8787 端口，然后自己去读 jsonl」。这对做实验够用，对别人不够用。

**已答的**：E3。一次 `/compact` 回本要 18–19 轮，不是预测锁定的 2–4 轮。
**阻塞的**：E1。缺的是断裂样本，不是分析能力——健康 agent 不断自己的前缀。
**未决的**：E2 到底测什么（见 `report/99-open-questions.md`）。

## 2. 立论没有变，而且空地经过验证

README 的「Why this repo exists」是这个项目全部价值的来源，一字不改：

> 几乎每个上下文压缩工具都在宣传 **token 降低率**。Token 不是钱。
> 一个缓存命中的 input token 只要标价的约 10%，而压缩通过重写历史来省 token，
> 会打断缓存前缀、让其后所有内容重新按全价计费。
> 所以「省了 40% token」和「账单变高」完全可以同时成立。
> **没有人公布美元数字。**

**空地是查过的，不是假设的**（2026-09-03，GitHub 搜索，五组关键词）：

| 项目 | ★ | 是什么 |
|---|---|---|
| `masteragentcoder/agentcache` | 5 | 缓存感知的**编排**，不是诊断 |
| `Nver-theless/codex-cache-monitor` | 1 | 只覆盖 Codex 的**可视化面板** |
| `Arsenalfleer78/prompt-caching` | 1 | 最接近，几乎是空的 |
| `agiwhitelist/tokdiet` | 33 | 压缩代理，**报 token 不报钱** |
| `khankaif/ContextQuant` | 4 | 同上 |

结论：**有面板，有压缩工具，没有诊断器。** 没有人回答「你的前缀在哪一步断的、
为什么、按当前定价这个月多花了多少」。

## 3. 要长成什么：诊断器，不是报告

报告是获客，**仪器才是产品**。这个区分决定了后面所有取舍。

现在的输出是一个 tally——「命中率 31.2%」。那是**观测**，不是**建议**。
目标输出是这样的：

```
缓存命中率  31.2%   （同类 agent 工作负载基线约 65%）

前缀断裂归因（共 8,412 次未命中）：
  62%  system prompt 第 3 行含动态内容
       "Current time: ..."  ← 每次请求都变
       估算月度损失  $1,847
  24%  工具定义顺序不稳定
       估算月度损失  $712

建议按收益排序：
  1. 把时间戳移到消息末尾            省 $1,847/月
  2. 工具定义按名称排序后再序列化      省 $712/月
```

差别不在展示，在**归因**。「断了」这个信息 provider 自己就给了；
「因为哪个字段」才是这个仓库能加的东西，也是 `attribute.py` 存在的理由——
它离线复现 Anthropic 的 `cache_miss_reason`（所以对不提供该接口的 provider 也能用），
并**下钻到具体 tool / message index / field**，比官方粒度细一层。

## 4. 两种形态，要在写第一行 CLI 之前选

| | 一次性诊断 | 持续检查 |
|---|---|---|
| 用法 | 装上、跑一周、看报告、改完卸载 | 进 CI，每个 PR 报「缓存命中率掉了 12%」 |
| 留存 | 低（问题修好就没用了） | 高（每次改动都可能引入回归） |
| 实现难度 | 低 | 高（要基线、要阈值、要归因稳定到能当门禁） |
| 采纳阻力 | 低（改一个 base_url） | 高（要进别人的流水线） |

**倾向持续检查**，因为诊断器修好即卸载的宿命躲不掉，而「这个 PR 让缓存命中率掉了 12%」
是一条能进 CI 的、可复现的断言。但它要求归因足够稳定——**这正是 4.2 要验的东西**。

所以顺序是固定的：**先验归因，再选形态，最后写 CLI。** 反过来会写出一个
建在没验证过的归因上的产品。

## 5. 护城河，以及它什么时候会消失

**跨 provider 是唯一站得住的差异。** Anthropic 已经有 `cache-diagnosis`
（E1 就在用它做交叉验证）。如果各家都出原生诊断，单 provider 的诊断价值会被压缩到零。

但**没有厂商会帮你比较四家**。`providers.py` 把各家不同的缓存用量字段归一成
一个四元组，注册新 provider 却不给费率会直接测试失败——这道闸是为跨 provider 建的，
而它正好是护城河所在。

**会失效的情形**：某个可观测性平台（Langfuse / Helicone 一类）把前缀归因做进去。
它们今天报 token 数和延迟，不报「为什么没命中」。这中间的距离不大。

---

## 6. 门槛：4.2 不成立就停

E4 的预测 4.2 是「component 级归因 ≥4/5 与注入原因一致」。

**它不成立，这个方向就不成立**，因为工具的全部增量在「为什么断」；
只报「断了」的话，provider 自己就给了。

`docs/e4-tasks.md` §7 因此被显式地卡在 4.2 之后。这不是保守，是
避免把三个月投进一个没验证过的前提——上一个项目
（RepoCoach）停下来的理由正是「技术切片跑通了，但产品侧差异化空间有限」，
那个判断是对的，代价是它晚了一点才做出来。
