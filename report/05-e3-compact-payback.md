# E3 压缩的回本周期

> 这一章要回答：一次 `/compact` 要几轮才把自己的成本赚回来？

**实测：18–19 轮。predictions 3.1 押的是 2–4 轮。** [实测 2026-08-19]

数据：`capture-03.jsonl`，Opus 5，一次真实的 `/compact`（压缩前 6 轮、压缩后 46 轮）。
费率来自官方 pricing 页，经 `agentcostlab.pricing` 的核实闸。**n=1。**

## 实测

```
压缩前上下文  93,656
压缩后        71,470
砍掉          22,186 = 24%
压缩那一轮仍从缓存读到 49,537   ← 根本不是冷启动

一次性成本      $0.1916
之后每轮省下    $0.0111     （少缓存 22,186 token × $0.50/Mtok）
回本            18–19 轮
```

回本轮次对反事实模型里唯一那个自由参数不敏感：把「不压缩的话那一轮会写入多少」在
实测区间（0 / 中位数 571 / 最大 900）里扫一遍，结果只在 18 和 19 之间动。

## 推算错在哪：算术没错，三个输入全错

3.1 的理由是一段纸面推算。把它的算法保留，逐个换成实测输入：

| 换掉哪一项 | 回本轮次 |
|---|---|
| 原始推算（100k 上下文、砍 75%、全部重写、写入 1.25×） | **2.8** |
| 换成实测上下文 93,656 | 2.8 |
| 再换成**实测砍掉比例 24%**（而非假设的 75%） | **36.0** |
| 再换成**实测「只有 31% 是新写的」**（69% 仍命中缓存） | 10.4 |
| 再换成**实测写入档位 1h = 2×**（而非 1.25×） | **17.8** |
| 逐轮真实用量（脚本） | **18–19** |

最后一行与倒数第二行吻合，**说明那段推算的算术是对的**。错的是它的三个输入，而且
方向相反、互相抵消了一部分：

1. **压缩只砍了 24%，不是 75%。** 这是最大的一项，单独就把 2.8 推到 36。
2. **压缩后并非全部重新写入。** 系统提示、工具表、CLAUDE.md 共 49,537 token 原样
   命中缓存——「冷启动」这个词从一开始就不成立。这一项把 36 拉回 10.4。
3. **写入走的是 1h 档（2×），不是 5m 档（1.25×）。** 这一项把 10.4 推到 17.8。

第 3 项正是仓库此前算不出美元的原因之一：费率表当时只有一个 `cache_write` 字段，
装不下 Anthropic 的两档价（#46）。

## 这对「尽量延迟 compact」的建议意味着什么

survey 的建议方向没被推翻，但**理由和量级都变了**。回本要 18–19 轮，不是 2–4 轮，
所以在一段还剩不到二十轮的会话里主动压缩，成本上是亏的。

更根本的一点：**压缩省的是最便宜的那一项。** 缓存读取本来就只要 0.1×，砍掉的
token 每轮只省 $0.0111；而压缩自己要按 2× 写一遍。省的是打折品，付的是原价。

## 3.2 答不了

「回本轮次是否取决于会话长度」需要至少两次不同长度的压缩事件。现有数据只有一次。

结构上可以看出：每轮节省 = 砍掉的 token × 缓存读取价，是个常数；一次性成本也固定。
所以对**给定的砍掉量**，回本轮次与其后会话还有多长无关——会话长度决定的是
**你会不会走到回本那一刻**，而不是那一刻在第几轮。但砍掉量本身随压缩时的上下文
规模变化，所以这只是推导，不是实测。要坐实需要第二次压缩事件。

## 不在本章范围

只算钱。压缩之后模型是否做得更差，是另一个维度，本章不测，也不应被本章的成本结论
暗示为「压缩是免费的」。
