## E2 到底要测什么，尚未定

E2 的立论是「两类工具成本曲线相反，而生态用同一个指标报告它们」。查证 RTK 之后，这个前提对它不成立：

- predictions.md 2.1 引「RTK 自己 README 承认 50 轮只省 1.6%」作支撑，**README 里没有这句话**（钉死 commit 上六个 pattern 零命中）。那是 survey 作者的估算。
- RTK README 第二段自己写明：它压的是 bash 输出，**这不等于账单降同样比例**。

也就是说，混淆指标的是转述它的文章，不是工具本身。那么 E2 测的是「工具夸大」还是「转述失真」？**这两个是不同的实验**，设计和结论都不一样。在花钱跑行为臂之前必须先定。

同时，preventive / retroactive 这个二分容纳不了 lean-ctx——它确实重写历史，只是把改写限制在自己算出的缓存安全窗口内。**同样的结果，不同的机制**，而 2.3 的推理正是从这个分类出发的。

两条都已进 predictions.md 的 errata（2026-08-19），依据见 [../docs/e2-rig.md](../docs/e2-rig.md)。

## 抑制规则依赖一个未验证的布局假设

「分叉点落在最后一个 `cache_control` block 之后 → 缓存没断」这条规则，要求知道
可缓存前缀在**哪里**结束，也就是要求知道 provider 真实的请求布局
（假定为 `tools → system → messages`）。这是 Anthropic 文档的说法，本仓库没有独立验证。

- 对隐式缓存的 provider（无显式 `cache_control` 断点），该规则退化：没有断点就
  一律判「断了」。这是保守方向，但会高估断裂率。
- 归因器扫描组件的顺序（`order`）是一个**待测假设**；布局是一个**声明的前提**。
  二者曾被混为一谈，见 issue #24。

## 真实数据的回归测试在 CI 里跑不到

归因器有三个测试直接读 `data/raw/` 下的真实 capture（120 排列不变性、唯一一次真实断裂、两份 capture 对台账的全量比对）。原始 capture 含完整请求体不可入库，而脱敏后 `request_body` 被哈希、对归因毫无用处。**所以这三个测试在干净检出里会 skip**（实测：157 passed / 3 skipped，每条点名缺哪个文件）。

机制本身由合成用例在 CI 里覆盖。只在真实数据上才暴露的回归，CI 挡不住——这一层保护只存在于有数据的机器上。

## 仪器本身的已知盲点

- **`/compact` 之后的一轮观测不到 —— 暂定接受（2026-08-19，#42）。**
  决定由项目负责人做出，措辞是「先按方案 3 接受」——暂定，不是终局。下面的权衡分析
  是评审方的评估，不是决策者给出的理由，两者分开记以免后人误读。
  **重新开放的条件**：任何一次 capture 显示 compaction 造成的 miss 在成本上占大头，
  此决定即作废。
  代理用 `messages[0]` 认对话，而压缩会开出一段首条消息全新的对话，于是压缩后第一个
  请求发 `previous_message_id: null`，Anthropic 无从比对，`messages_changed` 永远
  拿不到。已实测（capture-03，`/compact` 标记在 `fec6a430` 的 message[2]）。

  另外两条路都被否决了：按 `(system, tools)` 指纹兜底串接会重演 #14 的串线，而现有
  闸门用的就是同一个 key、结构上抓不到；认 `/compact` 那个标记字符串则把代理绑死在
  Claude Code 的一个实现细节上，升级时会静默失效。**两者都在给一个尚未证明有价值的
  观测付真实的正确性风险。**

  代价必须写在结论里，而不是只写在这里：**E1 1.1 给出的成因分布，结构性地不包含
  compaction 造成的 miss**。所以那个分布是**条件分布**，不是总体分布，引用时必须
  带上这个条件。

  **compaction 占多大比例，不知道，也不猜。** 至今观测到的 5 次真实断裂全部另有成因
  （ttl 抖动 4 次、system 文本改动 1 次），且主因不在 survey 那六项里。

  E3（compaction 回本周期）不受影响——它本来就设计成靠 usage 台账算，不依赖官方裁决。

- **lineage key 自碰撞，闸门现在看得见一半。** 跨 lineage 体检闸的判据用的就是
  `_lineage_key` 本身，所以两段首条消息相同的对话在它眼里本来就是同一条，闸门恒真。
  碰撞的后果是 #14 那种「看起来合理的错误裁决」而非报错。

  这一条原本写的是「实测三份 capture、57 个 lineage 组零碰撞」。**那句话是错的。**
  三份 capture 里都有一个 `d725e692` 组（19 / 16 / 18 条记录），每条 2 条消息、
  内容各不相同——是 Claude Code 的 `<transcript>` 旁路调用，每次都是独立的一次性
  会话，共用同一个 `messages[0]`。碰撞一直存在，只是这些调用不带缓存，从未产生
  假断裂，所以没有任何东西显形。

  同一条里写的「独立判据（同一 lineage 含多条互不相连的链）已验证可用」也不成立：
  #72 实测了两种切链方式，按 threading 指针切看不到断点（代理的 `LAST_ID` 残留把
  两条链接上了），按「非追加」切则把每一次真实缓存断裂都误报成拼接——在这三份
  capture 上分别切出 63 / 49 / 134 条假拼接。

  真正可用的判据是**同一 lineage 组内消息条数严格变短**（一次对话只会追加），
  0 误报 / 303 条真实记录，已接进 `capture_health.py`（#72）。**但它只能看见
  「变短」那一类碰撞**：`d725e692` 那种条数恒定的碰撞它设计上看不见。目前靠
  采集侧的 nonce 预防（见 `docs/e4-injection-campaign.md`），仍缺一条等长碰撞的判据。
- 同一 lineage 的并发请求可能挂到错误的前驱上。主 capture 未观测到，但代理没有防护。
- 强制 `accept-encoding: identity` 关闭了压缩，本地带宽无所谓，但这意味着
  本仓库测得的 `request_bytes` 是未压缩值，不能当作线路上的字节数。
- `error` 字段是覆盖写而非追加，一条记录上的第二个错误会盖掉第一个。
